# Orrery
A Rust + TUI LLM orchestrator application

## Summary
An application for staging and executing LLM workflows with built in checks and guardrails per agent role. Designed to work in conjunction with MCP, Orrery functions as an automation design and orchestration implementation platform where user can create a workflow, associate agents and roles, ingest stepped implementations plans, and run automations as one off synchronized tasks or on a loop.

## Base Function
* CLI + TUI interface: May be run from project directory or pointing to the project directory. 'orrery' without a modifier and with or without an associated directory will start the tui. 'orrery' with a modifier will perform the associated task of the modifier within the cli. 
*Project and Agent Markdown: TOML files used for defining projects and agent roles. Markdown files used to store implementation steps, agent rules, and in depth role definitions.
* Agent Orchestration: User dictates primary orchestration agent > Orrery programatically moves through steps in implementation plan mark down and passes the next step to the orchestrator > orchestrator reads requirements and then passes the instructions to the appropriate agent(s) > agent(s) complete task and report to orchestrator > orchestrator then forwards task to the validation agents > validation agent(s) either confirm or deny step completion to orchestrator > orchestrator either allocates revised task to implementation agent(s) or sends okay confirmation to orrery > upon confirmation orrery marks the current task as complete and then cycles to the next step.
* MCP connection: can connect to local or remote MCP.
* Agent Association: can connect to both local and cloud agentic platforms
* Workflow Design: TUI interface with columns in central panel for designating steps and agent assignment. 

## Agents
* Local (Primary): Local agent association the focus for initial push. Design promotes using containerized agents, so connection and manipulation of docker is crucial. Model context TOML points to the location and environment to be spun up with necessary details to proceed. While multiple agents running simultaneously will be available as an option in workflow steps, resource management is a key facet of the app's function allowing a developer to seamlessly utilize multiagent workflows without having to go through the hassle and time consumption of toggling each of the agents and containers by hand.
* Cloud: Functionality will be comparable with the key difference being the required API key. This will NEVER be stored within the app or its files. Orrery will store ingested keys in the OS keychain and will retain the smallest footprint possible of sensitive data.
*Task Storage: Since resource management is a key component we won't attempt to run different workflow step agents simultaneously. Instead, we will have agents report in TOML file format for instruction references, state changes, etc. This serves us two fold by allowing indirect communication between deactivated and activated agents and serving as a checkpoint (should a step be interrupted, we have a fallback for the last instructions sent. This also has the added benefit of keeping context windows smaller with fresh agents spun up for each step and us performing the necessary caching for them.

## Workflow
* Interface: Main panel and landing screen has Orrery header followed by menu bar underneath. Menu bar contains option to ingest steps, execution type toggle (run or loop), repeat cycle count field (how many times the flow should cycle/how many steps to complete with 0 being run until out of steps), current cycle count, and increase and decrease step count. Below menu there are two main fields, steps to left in smaller column, and workflow space. Full width field parses live agent thought chain. Below model output is horizontal menu with settings, help etc. Interface will support mouse and keyboard.
* Stepped Implementation: Implementation plan held in an md file. Special character designation (eg '#') indicate start of a new step. Orrery parses text between designated special characters and passes it to the orchestration agent.
* Workflow: Developer can dictate how many steps are in a given workflow. Each step has its own column with the default number of columns being 3 (orchestrator, coder, validator), but a developer may opt to use fewer (minimum 2) Maximum number of steps to be 15 (I can't really fathom a reason someone would need that many since it cycles but I'd rather add it and not need it than need it and not have the option). Each column has a header dictating the agent's role. Once a role is selected the cell below is accessible and the developer can dictate what agent to associate. Except for orchestrator all other roles will allow for selecting additional agents after each agent is selected (maximum 15). Agents returning complete signal with validated TOML trigger the app to cycle active agents back to orchestrator to then pass off the task. Orchestrator is triggered between each task primarily for cursory validation and context separation as app scope is too rigid to account for all edge cases.
* Live Stream: Intended for monitoring and user validation, but never read or accessible by other agents. Stored in logs and is overwritten once predetermined volume is reached (tbd).

## Development
* Interface Validation: Components will be designed with aesthetics and user-friendliness in mind. Dumping items in is not permitted. All reasonable design constraints will be adhered to, and if they cannot be adhered to they will be reported to me before continuing. No arbitrary binding of modifier keys is permitted. Most common assignments will be left to their default state (eg ctrl + c will never be "close").
* CLI: While the TUI is the polish, the CLI will be a robust workhorse with fully realized commands and modifiers to allow all actions available in the TUI to also be available in the CLI. Standard modifiers will be used whenever relevant.
* Security and Versioning: Upon initiation latest release of any dependency is the only option. Reversion or older versions are not permitted. Crates with outstanding CVE's or RustSec notices are not permitted. Unmanaged repositories are not permitted (including unmanaged due to functional completeness or lacking other security warnings). NIST standards will ALWAYS be adhered to. Best Rust language practices will ALWAYS be adhered to with Rust Skills utilized for every step.
* Code Validation and Hygiene: Cargo tests will be created for every function and method utilization within the application. Tests will NEVER be bypassed, muted, or ignored. Null and non-functioning tests are not permitted. Cargo check, cargo fmt, and cargo clippy must be run upon completion of every step. Dirty code and ignored warnings are NOT permitted. 
* Styling: TUI interface should utilize the same color palette as Nebulous with a CRT amber on black retro-futuristic aesthetic
## Decisions (recorded 2026-11-11)
These settle ambiguities in the sections above. Where they conflict with earlier text, these win.
* **Terminology:** a *plan step* is a section of the implementation plan markdown. A *stage* is a workflow column (a role plus its agents). The "15 maximum" applies to stages.
* **Agents:** three backend kinds — local model endpoints (primary target), containerized agent CLIs, and cloud APIs. Local models do implementation work; a stronger agent handles orchestration, validation and follow-up instructions.
* **Concurrency:** agents within one stage may run in parallel (bounded). Agents from different stages never run at the same time. Stages with write access run one agent at a time unless the orchestrator assigns non-overlapping write scopes.
* **Pass rule:** a plan step passes only when every validator confirms and the orchestrator confirms. The orchestrator can't override a validator denial. After the retry limit, Orrery halts for the operator.
* **Cycle count:** the number of plan steps that must pass in Loop mode. 0 = run until out of plan steps. Ignored in Run mode (Run = exactly one plan step).
* **Two-stage workflows:** allowed. With no validator stage, Orrery's gate (configured MCP check tools) plus operator approval validate the step. Not recommended for regular use; meant for simple tooling or test runs.
* **Scope:** Orrery orchestrates only. Version control, builds and similar work happen through MCP tools (Nebulous, a git MCP, etc.) that Orrery calls at lifecycle hooks. Orrery's core stays domain-neutral: development is the first use, not the only one.
* **Keys:** standard keys keep their standard meaning. Ctrl+C interrupts the running task. No invented modifier chords.
* **Dependencies:** latest stable release at the time a dependency is added; `Cargo.lock` committed; every cargo command uses `--locked`. `cargo deny` blocks RustSec advisories, unmaintained crates, `openssl-sys` and unknown sources.
* **NIST:** NIST SP 800-218 (SSDF) for development practice, FIPS 180-4 (SHA-256) for integrity hashing, SP 800-63B-aligned handling of secrets.
* **Tests:** test every behavior and invariant, with a coverage floor measured by `cargo llvm-cov`, instead of one test per function.
* **Live stream:** shows live agent output. Reasoning appears only where the backend exposes it.
